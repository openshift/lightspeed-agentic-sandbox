# Agentic Tool-Output Redaction [PARTIALLY IMPLEMENTED: OLS-3939]

This file specifies the current `lightspeed-agentic-sandbox` behavior for tool-result redaction. It implements only the sandbox runtime portion of the broader OLS cross-repository policy and Agentic integration contract. Classic chat, operator configuration delivery, and Agentic UI handoff are not implemented by this repository and remain planned. This is not a claim of complete PII detection, certified DLP, or an OLS 2.0 release commitment.

## Runtime behavior

1. `DeepAgentsProvider` compiles the built-in MCP rules once when redaction is enabled and supplies them to the tool-result middleware. The middleware applies redaction at the actual tool-call return boundary, before returned `ToolMessage` content enters graph state. It handles messages nested in SDK `Command`, mapping, list, and tuple results. Each message is converted to text, processed by the sequential MCP rules, and returned with sanitized content and per-result metadata. This is sequential rule application, not a one-pass combined matcher.
2. The same sanitized result is used by subsequent inspection/model handling, normalized `ToolResultEvent` output, and native tool-span result capture. Inspection remains independently controlled: disabling inspection does not disable redaction. Synthetic `ToolMessage`s that do not arrive in an intercepted tool-call result are outside this redaction boundary.
3. A redaction or result-serialization failure fails closed before the tool result is returned to agent state. Tool-handler exceptions are converted to payload-free `ToolExecutionError`; raw exception messages are not forwarded as tool-result content.
4. Default rules cover credential assignments, JWT candidates, GitHub and AWS access-key patterns, `sk-` API-key candidates, bearer tokens, emails, formatted US/international phone numbers, and formatted US SSNs. Replacements use `[REDACTED:<category>]`; credential keys and `Bearer ` prefixes are retained. Standalone IPv4/IPv6 addresses and CIDRs are preserved. These heuristics do not guarantee detection of all sensitive data.
5. The rule engine returns sanitized text and per-category counts from the same application operation. The middleware includes `redacted`, `redacted_count`, and category counts in the internal `ToolResultEvent` projection. For results with replacements, it emits a metadata-only developer log containing the tool name and counts; it does not log raw or sanitized result text. Results without replacements do not emit a redaction log. The middleware does not create or close telemetry spans.

## Configuration and evidence

6. `LIGHTSPEED_TOOL_OUTPUT_REDACTION_ENABLED` controls this policy. It defaults to `true` when absent or empty. Only case-insensitive `true` and `false` are accepted; another value fails startup. Explicit `false` skips rule compilation and redaction, emits a warning, and intentionally allows unredacted results to flow to agent state, inspection/model input, normalized events, and native tool spans. It does not disable inspection. This opt-out means raw tool data may be sent to providers and retained in telemetry.
7. Native tool spans record the result supplied through the safe tool-result handoff: sanitized content by default, or raw content when redaction is explicitly disabled. This differs from the older inspection-only contract, which described raw native callback results. Inspection rejection does not restore raw content or erase the already-completed span. Span content-capture/export behavior remains governed by [audit-logging.md](audit-logging.md) and [data-collection.md](data-collection.md).
8. The current environment variable is a sandbox-local opt-out, not an operator-managed policy handoff. There is no runtime custom-rule configuration, shared Classic policy delivery, typed Agentic UI handoff, or per-reply UI indicator in this repository's implementation.
9. Python's standard-library `re` is used and provides no match-timeout protection. Keep built-in patterns controlled; do not claim protection against pathological regular-expression execution. Redaction is heuristic and is not complete PII detection or certified DLP.

## Verification

The sandbox implementation is covered by `tests/test_redaction_engine.py`, `tests/test_config.py`, `tests/test_tool_result_inspection_middleware.py`, `tests/test_deepagents.py`, `tests/test_deepagents_tool_spans.py`, `tests/test_trace_reconstruction.py`, `tests/test_batch.py`, and `tests/test_run_agent.py`. These tests exercise rule matching, default-on and opt-out configuration, safe result handoff, normalized events and native spans. They are offline tests; they do not establish live provider, operator, UI, or end-to-end product behavior.
